# Assumptions

Per the execution rules, ambiguities are resolved here with reasonable defaults rather than blocking on questions. Revisit any of these at any time — they're defaults, not commitments.

## Product

| # | Assumption | Rationale |
|---|---|---|
| 1 | Single user, single household. No multi-user accounts, no permissions system. | Matches "no mandatory account" principle; you are the only user. |
| 2 | One SQLite database file = one "book." No multi-book/multi-company support in MVP. | Keeps schema and UI simple. Business expenses are just a category, not a separate ledger. |
| 3 | Currency is single-currency, default **BDT (৳)**, configurable in Settings. | You're in Bangladesh; app should show correct symbol out of the box. Multi-currency is future scope. |
| 4 | "Family expenses" and "business expenses" are **categories/tags**, not separate modules. | Avoids duplicating expense logic. A category filter answers "how much did I spend on family/business this month" just as well as a separate module would. |
| 5 | DPS (Deposit Pension Scheme) is modeled as a **recurring savings goal** with a fixed monthly contribution and maturity date, not a separate financial instrument type. | It behaves like a recurring fixed contribution toward a goal — same shape as any other savings goal, just pre-filled with DPS-typical fields (tenure, monthly installment, maturity value). |
| 6 | Budgets are **monthly**, reset each calendar month. No custom budget periods (weekly/yearly) in MVP. | Matches the stated core questions, all of which are monthly. |
| 7 | "Fixed expenses" are recurring expense **templates** that auto-generate a pending entry each month, which you confirm/edit rather than the app silently posting them. | Prevents surprise numbers on the dashboard; keeps you in control, matches "confirmation dialogs where necessary." |

## Technical

| # | Assumption | Rationale |
|---|---|---|
| 8 | OS target for MVP is **Windows 10/11 only**. macOS/Linux builds are possible later since Tauri is cross-platform, but not tested or packaged in MVP. | Matches stated primary platform; avoids QA burden across 3 OSes for a personal tool. |
| 9 | Database file lives in the OS app-data directory (`%APPDATA%\personal-finance-manager\`) by default, with a Settings option to relocate it (e.g., into a synced folder like OneDrive) for the user's own backup convenience. | Standard, discoverable, and doesn't force cloud infra while still letting you opt into your own sync. |
| 10 | No auto-update mechanism in MVP. Updates are manual downloads from GitHub Releases. | Avoids background network calls, consistent with offline-first/privacy-first principles. Tauri's updater can be added post-MVP behind an explicit opt-in. |
| 11 | No telemetry, crash reporting, or analytics of any kind, ever, unless explicitly requested later. | Privacy-first principle. |
| 12 | State management: **Zustand** (not Redux). Forms: **React Hook Form + Zod**. Dates: **date-fns**. Animation: **Framer Motion**. | Each is lightweight, has first-class TypeScript support, and is proportionate to a small app — avoids the bloat a larger toolkit would add. |
| 13 | SQLite access goes through `tauri-plugin-sql` (official Tauri plugin) rather than a custom Rust data layer, unless a specific feature (e.g., encrypted DB) requires dropping to raw Rust commands. | Least custom code, official support, sufficient for local CRUD + aggregation queries. |
| 14 | PDF export is **post-MVP** (CSV export ships first). | Matches roadmap note "PDF export later if useful"; CSV alone answers the core questions and is far simpler to implement well. |

## UX / Design

| # | Assumption | Rationale |
|---|---|---|
| 15 | Visual language: dark-mode-first "glass" / futuristic dashboard aesthetic (translucent panels, subtle blur, soft glow accents, smooth motion), with a light mode that keeps the same structure but a flatter/cleaner treatment (heavy blur glassmorphism reads best in dark UI). | Directly requested. Documented fully in `docs/ui-ux/DESIGN_SYSTEM.md`. |
| 16 | Animation is used for state transitions and feedback (page transitions, number count-ups, chart draw-in, success states) but never blocks or slows the Quick Add flow — animations are skippable/instant on repeat fast entry. | "Great animation" and "10-second expense entry" are in tension; the resolution is that delight lives in the dashboard, not in the hot path. |
| 17 | Quick Add Expense opens as an overlay/command-palette-style modal (triggered by `Ctrl+E`) rather than navigating to a new screen. | Fastest possible entry; no navigation cost. |

| 18 | Light mode fills in the tokens `DESIGN_SYSTEM.md` doesn't spell out: `--text-primary: #0A0E17`, `--text-secondary: rgba(10,14,23,0.6)` (dark text for contrast on a light background), `--glass-border: rgba(10,14,23,0.08)` / hover `rgba(10,14,23,0.16)` (dark-tinted instead of white-tinted). Accent colors (`--accent-primary/success/warning/danger`) and the glass blur radius stay identical across themes. | Smallest change that satisfies "same token names, same roles" while keeping ≥4.5:1 contrast, which a white-on-white or white-border-on-white scheme would fail. |
| 19 | One extra radius token beyond the documented 20px card radius: `--radius-control: 12px`, for inputs/buttons/smaller controls, at roughly half the card radius. | `DESIGN_SYSTEM.md` only specifies the glass-card radius; smaller controls need something visibly tighter than 20px, and CLAUDE.md requires all radii to come from tokens, not hardcoded values. |
| 20 | When `backdrop-filter` is unsupported/non-performant, the glass fallback raises `--glass-surface` opacity (dark: 0.06 → 0.14, light: 0.7 → 0.92) instead of blurring, per the "non-blurred fallback" requirement in CLAUDE.md. | Keeps panels readable against a busy background without blur, without inventing a whole second color set. |
| 21 | Tauri app identifier is `com.arfinance.desktop`; CSP is locked to `default-src 'self'` plus the minimum `style-src 'unsafe-inline'` (component libraries set inline `style=""`), `img-src`/`font-src` `data:`, and `connect-src`/`asset:` scoped to Tauri's own IPC/asset protocols — no remote origins anywhere. | No product identifier or exact CSP string was specified; this is the tightest CSP that still lets the WebView load its own bundled assets and talk to Tauri's IPC, matching "Tauri CSP locked down" / "no remote content." |
| 22 | Phase 1's theme toggle persists to `localStorage`, not the `settings` table, even though `settings.theme` is seeded. It gets wired to the real DB-backed setting once generic settings read/write commands exist (Settings feature, later phase). | Phase 1 scope is the app shell only — no Tauri commands for settings CRUD exist yet, and adding one just for theme would be a feature built ahead of its phase. |
| 23 | Phase 4 KPI tiles show the animated count-up number only, without the "tiny sparkline" `DESIGN_SYSTEM.md`'s layout section mentions. | A per-tile sparkline needs its own trailing-days-of-data query per KPI and adds a second animated element to the highest-traffic screen; the count-up plus the four charts already answer the core "how am I doing this month" questions. Revisit if it's specifically requested. |
| 24 | The Pending Fixed Expenses widget on the Dashboard only renders when the dashboard's month selector is on the real current month, not when browsing a past/future month. | "Pending confirmation" is inherently a today concept (Phase 2 behavior); showing it while browsing e.g. last month would misleadingly suggest last month has unconfirmed items. |
| 25 | Dashboard charts don't ship a per-chart "table view" toggle; exact figures are reachable via hover tooltips, direct/legend labels, and the existing Expenses/Budgets screens (which are themselves full sortable tables). | A literal alternate table view per chart is a generic dataviz-accessibility nicety not called for by `DESIGN_SYSTEM.md` or `PHASE_4.md`, and the data is already fully reachable elsewhere in the app — building it now would be scope beyond what Phase 4 asks for. |
| 26 | The Spending by Category donut colors each slice with that category's own persistent `categories.color` (already used everywhere else — Budgets, Expenses, Pending Fixed Expenses) rather than a freshly generated chart palette, and shows every category with spend that month uncapped (no "Other" bucket). | Keeps one color meaning "one category" consistently across the whole app; a realistic month's spend rarely spans more than the ~14 seeded categories, so a synthetic grouping bucket isn't needed yet. |
| 27 | A DPS goal's "tenure" isn't a stored field — it's derived as whole months between the goal's own `created_at` and its `target_date` (rounded up on a partial month past the day-of-month anniversary), and `projectedMaturityCents = monthlyContributionCents × tenureMonths`. | Matches Assumption #5 (DPS is a recurring goal, not a separate instrument) — the `goals` table already has `monthly_contribution_cents`/`target_date`; adding a redundant stored tenure would let it drift out of sync with those two fields. |
| 28 | Goals only support archive (`is_active = 0`), never hard-delete, from the UI — there's no delete button for goals at all, only for individual savings entries. | Directly satisfies Phase 5's DoD wording ("archived, not hard-deleted if they have contributions") by never offering the destructive path in the first place, rather than building conditional logic that hard-deletes only when a goal happens to have zero contributions. |
| 29 | Logging savings against a goal auto-derives the entry's `type` from the goal's own type (`savings`→`goal`, `dps`→`dps`, `emergency_fund`→`emergency_fund`) instead of asking the user to pick a type redundantly; only ad-hoc entries (no goal selected) let the user choose between `general` and `emergency_fund`. | The entry type and the goal's type would otherwise have to agree by convention with no enforcement — deriving it removes a whole class of "picked the wrong type for this goal" mistakes. |
| 30 | Savings entries can be created and deleted from the Savings screen, but not edited in place (no "Edit entry" modal) — a correction is a delete-and-re-log. | Matches the smallest surface Phase 5 asks for ("savings entry logging... ad-hoc and against a goal"); an edit flow duplicates the create form for a rare correction case and can be added later if it's actually needed. |
| 31 | The Reports screen's "category breakdown table" covers expense categories only, not income sources/categories. | `PHASE_6.md`'s example fields (income, expenses, savings, net, budget adherence) are all *totals*; only expenses have a per-category budget concept to break down against. Income already has its own filterable list on the Income screen. |
| 32 | CSV import (`PHASE_7.md`'s "if time allows" item) is deferred to Post-MVP rather than built alongside backup/restore. | Backup/restore already covers "confidence that data can never be easily lost" (Phase 7's stated expected output) end-to-end; import needs its own column-mapping UI, dry-run preview, and validation surface that's substantial enough to deserve a dedicated pass rather than being squeezed in as a stretch item. |
| 33 | `tauri-plugin-sql` opens `"sqlite:pfm.db"` against `app.path().app_config_dir()`, not `app_data_dir()` — confirmed by reading the plugin's own `path_mapper` source, not documentation. Assumption #9 ("OS app-data directory") is Windows-accurate (`%APPDATA%` backs both config and data dirs there) but the two diverge on Linux/macOS. Any Rust code that touches the live DB file directly (backup/restore) must resolve its path the same way the plugin does, via `app_config_dir()`, not assume Assumption #9's wording literally. | Found the hard way: backup commands written against `app_data_dir()` failed with "No such file or directory" in manual testing. Recorded here so no future code repeats the mistake. |
| 34 | Every raw file copy of the live SQLite database (manual backup, pre-restore safety copy, pre-migration safety copy) is preceded by an explicit `PRAGMA wal_checkpoint(TRUNCATE)` against a connection to that same database. | The DB can run in WAL mode, where recent commits live in a `-wal` sidecar file until checkpointed and are invisible to a plain `std::fs::copy` of the main `.db` file — silently producing an incomplete backup. Found via manual exercise (a freshly-added expense was missing from a backup taken seconds later); the checkpoint makes every copy point-in-time-complete regardless of journal mode. |
| 35 | `UI_UX_GUIDE.md`'s Settings wishlist item "DB file location" (viewing/relocating the database file) is deferred past Phase 8 — Assumption #9's "Settings option to relocate it" is not built yet. | `PHASE_8.md`'s own task list and Definition of Done don't mention DB relocation; it needs a new Tauri command, live-pool handling, and a picker flow with roughly the same shape as Phase 7's restore — substantial enough to deserve its own pass rather than a Phase 8 add-on, and none of Phase 8's four DoD checklist items depend on it. |
| 36 | `UI_UX_GUIDE.md`'s error-state spec ("persistent toast... with a retry action") is satisfied by every error toast being non-auto-dismissing and explicitly dismissible (`toastStore.ts`, since Phase 1/2) — a literal per-toast "Retry" button wired to each failed call is not built. | A generic retry button would need a retry callback threaded through every one of the dozens of existing `showToast(message, 'error')` call sites across every screen — a cross-cutting refactor, not a Phase 8 polish item. "Never silently swallowed" is already fully met: the error stays on screen, named, until the user dismisses it or the underlying action is retried by re-clicking the original control. |
| 37 | Settings → Currency (`currencyStore.ts`) switches the display symbol only — it never converts stored amounts. Picking USD after entering data in BDT just relabels every existing cents value with `$` instead of `৳`; the numbers themselves don't change. | Amounts are integer cents with no currency column anywhere in the schema (`docs/database/SCHEMA.md`), and real FX conversion is explicitly listed in `ROADMAP.md`'s Future/Optional scope ("Multi-currency support") — out of scope for a Settings polish request. The picker's helper text says this explicitly so it can't be mistaken for real conversion. |
